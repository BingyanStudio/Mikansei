# Mikansei：让零散的学习与生活事务，逐步走向完成

> 一款以 To-do List 和 Checklist 为核心的个人事务管理产品，帮助用户及时记下事情、看清当前重点，并把任务推进到完成。
>
> 团队内部讨论稿 · 2026 年 10 月 20 日  
> 当前阶段：已有可试用原型，正在验证核心体验与跨平台能力。文中的用户扩展、验证方案和商业化方向属于产品建议。

## 1. 这个想法从哪里来

Mikansei 起于我自己的一个日常困扰：课堂作业、学生组织工作和生活琐事不断进入我的生活，但它们散落在不同地方。

老师在下课前布置作业，群里补充提交要求，课程平台规定截止时间；与此同时，还要记得打疫苗、洗衣服、给家里打电话。有些事情有明确时间，有些只有一个 DDL，有些则需要反复进行。

我在最初提出需求时说过：

> “之前的日程软件我认为是待办事项建立成本还是过高，让用户懒得现场写入日程。”

> “我还需要‘添加事项’提醒，例如每一节课下课的时候……这节课有什么作业么？DDL 是多久？”

这两句话决定了产品的起点：**一件事能否被完成，首先取决于它有没有及时被记下来，以及记录之后能否再次进入注意力。**

因此，Mikansei 想围绕任务的整个过程提供帮助：信息刚出现时容易记录，准备行动时容易找到，执行过程中容易推进，完成之后有清晰反馈。

## 2. 我们首先服务谁

第一批目标用户是**同时处理课程作业、社团事务与个人生活的大学生**。

这类用户的典型情况是：

- 信息来自课堂、群聊、课程平台和日历，需要自己整理成行动。
- 一件作业除了标题，还有提交平台、DDL、步骤和预计用时。
- 很多事情暂时无法确定什么时候做，但需要先记住。
- 经常在手机和电脑之间切换，希望继续处理同一批事项。
- 愿意管理任务，但不希望维护任务清单本身占用太多精力。

最初的需求来自我个人，尚不能代表所有大学生。校园人群是接下来优先验证的范围；其他个人事务管理场景可以在验证之后扩展。

## 3. 用户究竟需要什么

可以把核心需求表达为：

> 当我从课堂、群消息或生活中接到一件事时，我希望先用很小的成本把它接住；等我有时间处理时，能立即知道它有多紧急、在哪里做、需要做哪几步，并在合适的时候得到提醒。

| 任务过程 | 具体困难 | 用户期待 |
| --- | --- | --- |
| 收到信息 | 当时忙，来不及填写完整表单 | 先用一句话记下来，细节稍后补充 |
| 整理要求 | 截止时间、平台和原文散落各处 | 打开事项就能找到执行所需的信息 |
| 决定先做什么 | 多件事同时存在，轻重缓急难判断 | 一眼看到逾期、紧急和正在做的事情 |
| 开始执行 | 大任务缺少清晰的下一步 | 拆成可直接勾选的小步骤 |
| 持续推进 | 记完之后不再打开，普通提醒容易错过 | 在常用的系统界面看见任务，按需调整提醒 |
| 切换设备 | 手机记录，电脑处理，状态容易断开 | Checklist、完成状态和用时能够接续 |

这里值得验证的产品判断是：**降低记录与再次找到任务的成本，可能比增加更多管理选项，更能帮助这批用户持续使用。**

## 4. 解决方案：围绕一件事项连接整个过程

Mikansei 的基本流程是：

**及时记下 → 补充必要信息 → 看清当前重点 → 安排并执行 → 完成与回顾**

### 4.1 让记录发生得更早

一句话即可建立事项，不强制填写时间、分类和完整说明；需要时再补充提交平台、地点、预计用时与消息原文。

课表还可以成为记录的触发点：下课时提醒用户“这节课有没有作业？”。通知点入后，课程等已知信息可以预填，减少现场录入的负担。

群消息录入目前采用**用户主动复制粘贴、系统给出解析建议、用户核对保存**的方式。自动获取指定群消息是最初提出的期望，需要可靠且经授权的信息入口后再推进。

### 4.2 清单与日历“一体两面”

这是产品的重要设计原则：**截止时间和执行时段分别表达。**

| 信息 | 回答的问题 | 示例 |
| --- | --- | --- |
| DDL | 最晚什么时候完成？ | 周五 23:59 前提交作业 |
| 执行时段 | 打算什么时候做？ | 周四 19:00—20:00 写作业 |
| Checklist | 具体要完成哪些步骤？ | 阅读材料、完成题目、检查、提交 |

用户可以先只记录 DDL，再决定执行时间。同一事项在清单中展示进度，在日历中展示安排，完成状态、步骤与累计用时仍跟着这件事走。

系统日历中的已有日程也可以导入，减少重复录入；来源由用户选择，避免无关内容挤占清单。

### 4.3 让重要事项更容易被看见

首页突出已逾期、正在做和未完成事项，并结合重要级与时间排序。主屏幕小组件、锁屏实时活动和灵动岛提供更短的查看入口，降低反复打开 App 查清单的成本。

这些入口应突出当前需要行动的信息。展示范围、刷新和持续时间仍受系统机制影响，不能把它们理解为全天候后台监控。

### 4.4 从“记住任务”走向“推进任务”

Checklist 可以在清单卡片上直接勾选，减少反复进入详情的操作。用户可以标记“正在做”，用计时了解一件事投入了多久；循环事项则承担洗衣服等规律性事务。

提醒支持按事情的重要程度选择方式与强度。更强的催办应由用户主动选择，同时允许暂停和调整，避免提醒变成新的干扰。

### 4.5 给完成留下反馈，也建立长期使用的信任

完成后保留划线与当天记录，跨天进入历史，让用户看见当天的推进结果。

对这类产品，数据连续性本身也是体验：Checklist 勾选、完成状态、计时和备注，需要在保存、更新与切换设备后保持可信。本机保存、备份与同步错误提示都服务于这个要求。

## 5. 一个典型使用场景

以下是用于讲解产品的示例：

1. **上午下课。** 手机提醒登记作业，我输入“高数习题”，先把事情记下来。
2. **下午收到群通知。** 粘贴相关文字，核对周五截止、提交到课程平台等信息，并拆成几个步骤。
3. **晚饭后安排时间。** 看清单决定先处理这件事，再在日历中安排今晚的一小时；作业的原 DDL 继续保留。
4. **开始做作业。** 标记“正在做”，逐步勾选 Checklist，手机上的可见入口帮助我记住当前重点。
5. **完成并提交。** 我明确标记完成，当天仍能看到划线记录，之后可以回看投入时间。

这个场景串起了产品想创造的价值：**一条零散信息逐步变成可执行、可推进、可确认完成的事项。**

## 6. 目前已经走到哪里

Mikansei 已经有可试用原型，能够支持团队围绕实际操作讨论。以下依据当前项目资料整理，不代表所有平台均已完成真实设备验收。

| 范围 | 当前进展 |
| --- | --- |
| 核心清单 | 已有快速添加、事项类型、Checklist、优先级、DDL、完成与历史、循环和计时 |
| 校园场景 | 已有课表导入、课后登记和粘贴消息辅助解析；具体学校的数据适配仍需验证 |
| 日历与系统入口 | 原生版已有日历联动、小组件、提醒与实时活动实现；跨平台测试版的相关系统能力仍需真机验证 |
| 多设备 | 原生版已有 iPhone、Mac 与所选 iCloud Drive 文件夹同步方案；Flutter 测试版 Mikanseta 已加入账户同步和共享文件夹同步实现，真实多端流程仍待验收 |
| 平台扩展 | 已有独立的 Flutter 测试版，推进 iOS、Android、macOS 的体验复用与维护 |

需要向团队说明的边界：

- 目前没有自动读取指定 QQ 群，也没有完成与 HUSToday 的直接连接。
- 不同系统、不同版本的提醒和日历能力尚未完全对齐。
- 跨设备同步、后台提醒和系统组件需要继续验证真实使用中的可靠性。
- 原型与测试包尚不能代表成熟的公开分发产品。

对外介绍统一使用 **Mikansei** 作为产品名称；Mikanseta 是当前跨平台迁移的独立测试版本。

## 7. 希望建立的产品特色

我们希望通过以下组合形成辨识度：

1. **围绕校园事务的记录时机。** 下课登记、作业平台与消息辅助录入，直接回应“事情最容易在哪里漏掉”。
2. **围绕当前行动的信息组织。** 清单、日历、Checklist 和正在做状态，共同帮助用户决定并推进下一步。
3. **利用系统入口降低查看成本。** 手机上的可见性与电脑上的处理效率接续起来。

这些是差异化方向，尚未经过系统竞品比较或用户研究验证。团队应重点观察用户是否愿意把已有任务迁入、持续记录，以及在忙碌时是否仍能顺手使用。

界面也应服从这个方向：重要内容清楚，常用操作短，详细设置按需出现。原生版的绿色与跨平台测试版的牛皮浅棕可以承担视觉识别；角色与品牌元素服务于识别和情绪体验。

## 8. 下一步先验证什么

建议先邀请 **8—12 名有课程、社团或学生工作任务的大学生，连续试用两周**。这是建议的验证方案，尚无对应用户数据。

| 核心假设 | 建议观察的证据 |
| --- | --- |
| 快速添加和课后提醒能减少漏记 | 任务录入耗时、登记提醒后的实际录入、回访中发现的漏记情况 |
| 清单与 Checklist 能帮助开始行动 | 用户是否主动拆步骤、是否知道下一步做什么、哪些操作造成中断 |
| 小组件和实时活动值得持续开启 | 用户是否实际使用、是否减少找任务的步骤、是否感到打扰 |
| DDL 与执行时段分开更符合习惯 | 用户能否正确理解和修改两种时间，是否出现错期与重复安排 |
| 数据与提醒足够可信 | 丢失、重复、同步冲突、提醒失败，以及用户发现问题时能否自行恢复 |

完成率可以作为辅助信息，但任务难度、数量和截止时间不同，不能单凭勾选数量判断效率提升。“让用户不拖延”目前是愿景，需要通过行为观察与访谈检验。

## 9. 建议的推进顺序

**第一步：打磨核心使用过程。** 优先保证快速添加、查看重点、勾选步骤、安排时间和保存数据顺畅可靠，让用户能够连续使用。

**第二步：验证校园场景与系统入口。** 观察课后登记是否发生在合适时机，提醒强度是否可接受，小组件是否展示了真正需要的信息。

**第三步：完成跨平台与多端接续。** 在真实设备上验证同步、改期、删除、离线恢复和提醒行为，使平台扩展承接已经成立的体验。

自动消息接入、更多学校数据源和商业化可以在核心价值得到验证后讨论。付费价值与用户付费意愿都尚未确认，现阶段优先争取真实的重复使用。

## 10. 我希望团队一起参与什么

- **产品与研究：** 找到相似的真实用户，验证漏记、录入成本和提醒需求。
- **设计：** 打磨从记录到执行的关键操作，让首屏重点和信息层级更清楚。
- **工程：** 提高数据、同步与系统提醒的可靠性，明确各平台的体验边界。

团队接下来最值得讨论的问题是：**当事情不断从课堂、群聊和生活中涌入时，Mikansei 能否成为用户愿意持续依赖的那张行动清单？**
